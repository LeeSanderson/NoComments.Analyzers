# NOC0003: Do not use documentation comments

| Property | Value |
|---|---|
| ID | NOC0003 |
| Category | Maintainability |
| Default severity | Warning |
| Code fix | Remove comment |

Message: `Documentation comment: express the intent in code instead`

A documentation comment is a `///` or `/** */` comment in a project that generates documentation (`GenerateDocumentationFile` is `true`). A block of consecutive `///` lines is one documentation comment, so it is reported as one diagnostic.

## Why

Comments drift out of step with the code they describe. The compiler checks only the XML shape of a documentation comment, not whether its text is still true. Express the intent through names, types and tests instead: those are checked on every build.

NOC0003 has its own ID so that you can treat documentation comments differently from other comments. For example, set NOC0003 to `none` for a public library and keep NOC0001 and NOC0002 as errors.

## Examples

Reported (in a project that generates documentation):

```csharp
/// <summary>
/// Returns true when the customer can place an order.
/// </summary>
/// <param name="customer">The customer to check.</param>
public bool Check(Customer customer) => customer.IsVerified && !customer.IsSuspended;
```

One diagnostic for the whole `///` block.

Not reported:

```csharp
public bool CanPlaceOrder(Customer customer) => customer.IsVerified && !customer.IsSuspended;
```

## Not reported

- **Directives.** `#region`, `#pragma`, `#nullable` and the other preprocessor directives are not comments.
- **Shebang lines** and **disabled `#if` text** (code inside an `#if` branch that is not compiled).
- **Generated code.** Files that Roslyn's generated-code detection classifies as generated (for example a `// <auto-generated/>` header, or a `.g.cs` or `.designer.cs` file name) are not analyzed. The one exception is a comment a person wrote in the C# of a Razor file (`.razor` or `.cshtml`): it is reported at its position in the Razor file, but the comments the Razor generator adds itself are never reported.
- **HTML comments** (`<!-- -->`) in Razor files. They are markup, not comments.
- **This form's boundary.** NOC0003 is reported only when the project generates documentation. In a project that does not, the compiler reads `///` and `/** */` as ordinary comments: each `///` line is reported as [NOC0001](NOC0001.md) and each `/** */` comment as [NOC0002](NOC0002.md). Changing `GenerateDocumentationFile` therefore moves these comments between NOC0003 and NOC0001/NOC0002. A comment that starts with four or more slashes (`////`) and the empty comment `/**/` are never documentation comments.

### CS1591 and `GenerateDocumentationFile`

With `GenerateDocumentationFile` set to `true`, the compiler reports CS1591 ("Missing XML comment for publicly visible type or member") for every public member without a documentation comment. NOC0003 asks you to remove those same comments, so the two rules pull in opposite directions. Pick one of these:

- Keep `GenerateDocumentationFile` set to `true` and add `CS1591` to `<NoWarn>`. `///` and `/** */` are then reported as NOC0003.
- Set `GenerateDocumentationFile` to `false`. CS1591 is not reported, and `///` and `/** */` are reported as NOC0001 and NOC0002.

NoComments does not change either setting for you.

## Code fix

The **Remove comment** code fix deletes the whole documentation comment and tidies the whitespace it leaves behind. It does not reformat anything else.

- **Own line:** a comment on lines of its own is deleted together with those lines, so no empty lines are left.
- **Before code:** a comment with only whitespace to its left is deleted together with the spaces to its right.
- **After or between code:** a comment is deleted together with the spaces to its left (or to its right, when there are none on the left).
- **Blank lines:** a block removed from between two blank lines also removes one of the blank lines. A block at the top of the file removes the blank lines after it. A block at the end of the file removes the blank line above it.
- `#region` names, braces and other formatting are not changed.

Before and after:

```csharp
/// <summary>
/// Adds two numbers.
/// </summary>
/// <param name="a">First.</param>
public int Add(int a, int b) => a + b;

/** <summary>Old style.</summary> */
public int Sub(int a, int b) => a - b;
```

```csharp
public int Add(int a, int b) => a + b;

public int Sub(int a, int b) => a - b;
```

**Fix All** (document, project and solution) is supported. It removes all the targeted comments in one pass and gives exactly the same text as removing them one at a time.

In Visual Studio and VS Code with C# Dev Kit, the fix is offered for `.cs` files. The IDEs offer no code actions in Razor files. To remove C# comments from `.razor` and `.cshtml` files, run Fix All from the command line:

```shell
dotnet format analyzers --diagnostics NOC0003 --include-generated
```

`--include-generated` is needed because Roslyn sees the C# in a Razor file only through the generated code. The fix edits the Razor file itself, never the generated C#, and follows the same whitespace rules.

## Suppression

All the standard .NET suppression mechanisms work:

- `.editorconfig`: `dotnet_diagnostic.NOC0003.severity = none` (or `suggestion`, `warning`, `error`). Each rule's severity can be set separately.
- `#pragma warning disable NOC0003` and `#pragma warning restore NOC0003`.
- `[SuppressMessage("Maintainability", "NOC0003")]` on a member or type.
- A global suppression: `[assembly: SuppressMessage("Maintainability", "NOC0003", Scope = "type", Target = "~T:Widget")]`.
- `<NoWarn>$(NoWarn);NOC0003</NoWarn>` in the project file.

Under `TreatWarningsAsErrors`, NOC0003 is reported as an error. There is no comment-based suppression syntax.
