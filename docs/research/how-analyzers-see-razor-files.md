# How analyzers see Razor files

Research for issue #5. Question: for `.razor` (Blazor) and `.cshtml` (MVC / Razor Pages) files, do Roslyn analyzers run on the generated C#? Is that C# classed as generated code? Do C# comments in `@code` / `@{ }` blocks reach the generated C#, and do diagnostics map back to the Razor file? Can an analyzer see Razor comments (`@* *@`) or HTML comments (`<!-- -->`)? What do existing analyzers that target Razor do?

## Short answer

| Question | Answer | Basis |
|---|---|---|
| Do analyzers run on Razor-generated C#? | Yes. The Razor compiler is a Roslyn source generator. Its output is part of the compilation, so analyzers see it. | Source + experiment |
| Is it classed as generated code? | Yes, for two separate reasons: the hint name ends in `.g.cs`, and the file contains `// <auto-generated/>`. So `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)` hides **all** of it, including the user's own C# comments. | Source + experiment |
| Are C# comments in `@code`, `@functions`, `@{ }` and `@( )` carried into the generated C#? | Yes, verbatim, as ordinary Roslyn comment trivia. | Experiment |
| Do diagnostics map back to the `.razor` / `.cshtml` file? | Yes. Razor emits `#line (l,c)-(l,c) "file.razor"` around user C#. Build output shows the warning at the `.razor` / `.cshtml` line and column. | Experiment |
| Are Razor comments `@* *@` in the generated C#? | No. They are dropped by the Razor compiler. | Experiment |
| Are HTML comments `<!-- -->` in the generated C#? | `.razor`: no, components drop them. `.cshtml`: yes, but only as text inside a string literal passed to `WriteLiteral(...)`, not as a comment. | Source + experiment |
| Can an analyzer see `@* *@` and `<!-- -->` at all? | Yes, as raw text. The Razor SDK passes every `.razor` / `.cshtml` file to the compiler as an `AdditionalFiles` item, so `AnalysisContext.Options.AdditionalFiles` has the full source text. The analyzer would have to find comments itself; the Razor syntax tree API is `internal`. | Source + experiment |
| What do existing Razor-targeting analyzers do? | ASP.NET Core's own component analyzers use `GeneratedCodeAnalysisFlags.Analyze \| ReportDiagnostics` so they can see the Razor-generated C#. | Source |

## Environment for the experiment

Facts marked **[verified]** were checked with a throwaway experiment (outside this repo):

- .NET SDK 10.0.403 (Roslyn `5.9.0-1.26523.112`), Windows 11.
- Projects from `dotnet new blazor --interactivity None --empty`, `dotnet new webapp` (Razor Pages) and `dotnet new mvc`, with `EmitCompilerGeneratedFiles=true`.
- A probe analyzer (`Microsoft.CodeAnalysis.CSharp` 4.8.0) with two `DiagnosticAnalyzer`s that report every comment trivia whose text contains `PROBE`:
  - `PRB001`: `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None)`. This is the planned NoComments configuration.
  - `PRB002`: `ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics)`.
  - Each diagnostic records the trivia kind, the tree's file path, `Location.GetMappedLineSpan()` and `SyntaxTreeAnalysisContext.IsGeneratedCode`. A compilation action also lists `.razor` / `.cshtml` entries in `AdditionalFiles`.
- Each Razor page got this content (with `@functions` in place of `@code` in `.cshtml`):

```razor
@* PROBE razor comment *@
<!-- PROBE html comment -->
<p>@(1 /* PROBE inline expression block comment */ + 1)</p>
@{
    // PROBE statement block line comment
    var x = 1; /* PROBE statement block block comment */
}
@code {
    // PROBE code block line comment
    /* PROBE code block block comment */
    /// <summary>PROBE code block doc comment</summary>
    private int Y() => 2;
}
```

## Findings

### 1. Razor is a source generator, and analyzers run on its output

Since .NET 6 the Razor SDK compiles `.razor` and `.cshtml` with a Roslyn source generator. The generator now lives in the `dotnet/roslyn` repo; `dotnet/razor` is archived and its README says "Razor compiler and tooling has moved into the dotnet/roslyn repository" ([dotnet/razor README](https://github.com/dotnet/razor), [dotnet/razor#13021](https://github.com/dotnet/razor/issues/13021)).

The generator adds one C# file per Razor file with `context.AddSource(hintName, csharpDocument.Text)` ([`RazorSourceGenerator.cs`](https://github.com/dotnet/roslyn/blob/3ba333703c4833834cd6669f85ce9cebb8624330/src/Razor/src/Compiler/Microsoft.CodeAnalysis.Razor.Compiler/src/SourceGenerators/RazorSourceGenerator.cs)). Generated trees are part of the compilation that analyzers run on.

**[verified]** In all three projects the probe saw one tree per Razor file, for example `obj/Debug/net10.0/generated/Microsoft.CodeAnalysis.Razor.Compiler/Microsoft.NET.Sdk.Razor.SourceGenerators.RazorSourceGenerator/Components/Pages/Home_razor.g.cs` and `.../Pages/Index_cshtml.g.cs`.

### 2. The Razor-generated C# is classed as generated code (twice over)

Roslyn decides "generated" in `GeneratedCodeUtilities` ([source](https://github.com/dotnet/roslyn/blob/main/src/Compilers/Core/Portable/SourceGeneration/GeneratedCodeUtilities.cs), commit `fa098b0`):

- `IsGeneratedCodeFile`: file name starts with `TemporaryGeneratedFile_`, or the name without its extension ends with `.designer`, `.generated`, `.g` or `.g.i`.
- `BeginsWithAutoGeneratedComment`: a comment in the leading trivia of the root contains `<autogenerated` or `<auto-generated`.
- `GetGeneratedCodeKindFromOptions`: an explicit `generated_code = true | false` in `.editorconfig` / `.globalconfig` takes precedence over both.

The Razor generator trips both automatic checks:

- Hint name: `GetIdentifierFromPath` appends `.g.cs` (for example `Home_razor.g.cs`, `Index_cshtml.g.cs`) ([`RazorSourceGenerator.Helpers.cs`](https://github.com/dotnet/roslyn/blob/3ba333703c4833834cd6669f85ce9cebb8624330/src/Razor/src/Compiler/Microsoft.CodeAnalysis.Razor.Compiler/src/SourceGenerators/RazorSourceGenerator.Helpers.cs)).
- Header: `RazorCSharpDocumentWriter` writes `#pragma checksum ...`, then `// <auto-generated/>`, then `#pragma warning disable 1591` ([`RazorCSharpDocumentWriter.cs`](https://github.com/dotnet/roslyn/blob/3ba333703c4833834cd6669f85ce9cebb8624330/src/Razor/src/Compiler/Microsoft.CodeAnalysis.Razor.Compiler/src/Language/RazorCSharpDocumentWriter.cs), around line 157).

**[verified]** `IsGeneratedCode` was `true` for every `*_razor.g.cs` and `*_cshtml.g.cs` tree. **`PRB001` (flags `None`) reported nothing in any Razor file.** `PRB002` (flags `Analyze | ReportDiagnostics`) reported every C# comment.

Consequence: with the planned `GeneratedCodeAnalysisFlags.None`, NoComments reports **nothing** in `.razor` / `.cshtml` files. Hand-written `.razor.cs` / `.cshtml.cs` code-behind files are ordinary source (verified: `Index.cshtml.cs` had `isGenerated=False`) and are covered as usual.

### 3. C# comments in Razor code blocks reach the generated C#, with `#line` mapping

**[verified]** All six C# comments in the probe reached the generated C# as normal Roslyn trivia (`SingleLineCommentTrivia` / `MultiLineCommentTrivia`) in both `.razor` and `.cshtml`:

- inside an explicit expression `@( ... )`,
- inside a statement block `@{ ... }`,
- inside `@code { ... }` (`.razor`) and `@functions { ... }` (`.cshtml`).

Razor wraps each block of user C# in an enhanced `#line` directive, for example:

```csharp
#line (12,3)-(15,1) "C:\...\Components\Pages\Home.razor"

    // PROBE statement block line comment
    var x = 1; /* PROBE statement block block comment */

#line default
#line hidden
```

`Location.GetMappedLineSpan()` on those comments returned `HasMappedPath = true` and the `.razor` / `.cshtml` path. The build printed the warnings at the Razor location, for example `Home.razor(13,5): warning PRB002` and `Index.cshtml(16,5): warning PRB002`. Column numbers matched the comment's position in the Razor file.

Comments that Razor itself writes sit outside these mapped regions. **[verified]** In `Home_razor.g.cs`, `// <auto-generated/>` (line 2) and `// language=Route,Component` (line 81) had `HasMappedPath = false`. So "mapped to a `.razor` / `.cshtml` path" cleanly separates user-written C# comments from Razor's own scaffolding comments.

### 4. `///` is not a documentation comment unless documentation is enabled

**[verified]** Side finding that applies to every file, not only Razor. Without `GenerateDocumentationFile`, a `///` comment came back as `SingleLineCommentTrivia` in both `Program.cs` and `Home.razor`. With `-p:GenerateDocumentationFile=true`, it came back as `SingleLineDocumentationCommentTrivia` (and the diagnostic span started after `///`). This is the compiler's `DocumentationMode` (`None` unless `/doc` is passed). The analyzer must treat both trivia kinds as comments, and must not rely on `///` being doc-comment trivia.

### 5. Razor comments and HTML comments never reach the C#

**[verified]** None of the generated files contained `PROBE razor comment`. Razor comments are removed by the Razor parser and are not lowered into C#.

HTML comments:

- **`.razor`**: not in the generated C#. **[verified]** The lowering phase for components has `VisitMarkupCommentBlock` with the body comment "Comments are ignored by components. We skip over anything that appears inside." ([`DefaultRazorIntermediateNodeLoweringPhase.cs`](https://github.com/dotnet/roslyn/blob/3ba333703c4833834cd6669f85ce9cebb8624330/src/Razor/src/Compiler/Microsoft.CodeAnalysis.Razor.Compiler/src/Language/DefaultRazorIntermediateNodeLoweringPhase.cs), around line 2012).
- **`.cshtml`**: **[verified]** present, but only as markup text inside a string literal: `WriteLiteral("<!-- PROBE html comment -->\n<p>");`. This is not comment trivia. An analyzer could only find it by searching string literals, and it would have no `#line` mapping back to the `.cshtml` file (it sits in a `#line hidden` region).

### 6. The raw Razor source is available to analyzers as `AdditionalFiles`

The Razor SDK adds every Razor input to `AdditionalFiles` so that the source generator can read it (`sdk/10.0.403/Sdks/Microsoft.NET.Sdk.Razor/targets/Microsoft.NET.Sdk.Razor.SourceGenerators.targets` in the installed SDK, lines 50-72: `<!-- Pass razor files to the compiler. -->` ... `<AdditionalFiles Include="@(_RazorAdditionalFile)" />`). `.cshtml` files are added only when `RazorCompileOnBuild` is not `false`. The same targets mark the `TargetPath` and `CssScope` metadata as compiler-visible.

Analyzers receive the same items through `AnalyzerOptions.AdditionalFiles` ([Roslyn docs: Using Additional Files](https://github.com/dotnet/roslyn/blob/main/docs/analyzers/Using%20Additional%20Files.md)).

**[verified]** The probe's compilation action saw every `.razor` file in the Blazor project and every `.cshtml` file in the Razor Pages and MVC projects. `GetText()` returned the full source, including `@*` and `<!--`.

What this does **not** give:

- **A parser.** The Razor syntax tree types (for example `RazorCommentBlockSyntax`, `MarkupCommentBlockSyntax`) are `internal sealed` in `Microsoft.CodeAnalysis.Razor.Compiler`. An analyzer would need its own scanner for `@* ... *@` and `<!-- ... -->`, and it must skip these sequences inside C# strings, C# comments, `<script>` / `<style>` content and HTML attribute values. That is a small lexer, not a regex.
- **A path through generated-code filtering.** A diagnostic in an additional file is created with `Location.Create(path, textSpan, linePositionSpan)` and reported from a compilation (or additional-file) action. Generated-code filtering does not apply to these locations, so they work with `GeneratedCodeAnalysisFlags.None`.
- **Code fixes.** A Roslyn `CodeFixProvider` works on `Document`s. Additional files are `TextDocument`s, so a standard code fix cannot edit them. Not verified empirically here; the follow-up should confirm before promising a fix for Razor or HTML comments.

### 7. Editorconfig `generated_code` can override the classification

**[verified]**

- `.editorconfig` with `[*.cs]` and `generated_code = false` made `PRB001` (flags `None`) report all six C# comments in `Home.razor`. It also flips every other `*.g.cs` in the project, so it is too broad.
- A narrower section `[{*_razor.g.cs,*_cshtml.g.cs}]` with `generated_code = false` made `PRB001` report the six comments in `Index.cshtml` and nothing else.

This is a consumer-side switch. It also changes the behaviour of every other analyzer in the project for those files, and it relies on the Razor hint-name convention (`_razor.g.cs`, `_cshtml.g.cs`), which is an implementation detail.

### 8. What existing analyzers that target Razor do

- **ASP.NET Core component analyzers** (`Microsoft.AspNetCore.Components.Analyzers`, BL0001 and others) call `context.ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.Analyze | GeneratedCodeAnalysisFlags.ReportDiagnostics)` so they run on the Razor-generated C# ([`ComponentParameterAnalyzer.cs`](https://github.com/dotnet/aspnetcore/blob/4cd19087e97e56ac3dcf07c60a7949502a7321fa/src/Components/Analyzers/src/ComponentParameterAnalyzer.cs)). They work on symbols, not comments, and rely on `#line` mapping for locations.
- **The Razor compiler** reports its own `RZ*` diagnostics directly against `.razor` / `.cshtml` files from its own parser. That is not available to third-party analyzers (internal API).
- I found no primary-source example of a third-party Roslyn analyzer that scans Razor markup through `AdditionalFiles`. The mechanism is standard (finding 6), but this repo would be breaking new ground.

## Not verified

- **IDE behaviour.** Everything above is from `dotnet build`. Whether Visual Studio / VS Code (C# Dev Kit) show these diagnostics live in the `.razor` editor, and with the same mapping, was not tested.
- **Code fixes in Razor files.** Whether a code fix on a diagnostic mapped through `#line` into a source-generated document can edit the `.razor` file was not tested. Source-generated documents are read-only in the Roslyn workspace, so expect that it cannot without extra work.
- **Older SDKs.** Only SDK 10.0.403 was tested. The `.g.cs` hint name and the `// <auto-generated/>` header are long-standing, but older Razor versions were not checked.

## Implications for "What a comment means in Razor files"

This is input for the grilling ticket, not a decision. The options:

1. **Out of scope by default.** Keep `GeneratedCodeAnalysisFlags.None`. Razor files report nothing, and code-behind `.razor.cs` / `.cshtml.cs` files are covered as normal. Users can opt in with `generated_code = false` for `[{*_razor.g.cs,*_cshtml.g.cs}]` (finding 7), at the cost of affecting other analyzers.
2. **C# comments in Razor only.** Switch to `Analyze | ReportDiagnostics`, and in generated trees report only comments whose mapped location is a `.razor` / `.cshtml` file (finding 3). Ordinary generated code (no mapping) stays excluded, and Razor's own `// <auto-generated/>` and `// language=...` comments are not reported. Cost: the analyzer now parses every generated tree, and the "generated code is excluded" rule becomes "generated code is excluded, except C# that Razor maps back to a Razor file". The glossary would need that nuance. Code fix support for these is uncertain.
3. **Option 2 plus Razor and HTML comments.** Also scan `AdditionalFiles` with a hand-written lexer for `@* *@` and `<!-- -->` (finding 6). This works with `None`, but needs a small Razor-aware scanner, separate diagnostic IDs or a shared ID, and probably no code fix.
4. **Separate rule IDs per comment form.** Whatever is chosen, Razor comments, HTML comments and C# comments in Razor could have their own IDs, so users can turn off, for example, HTML comments (which are sent to the browser in `.cshtml` and may be intentional, such as conditional comments or licence banners).

Questions the grilling ticket should settle:

- Is an HTML comment a "comment" for this analyzer? In `.cshtml` it is shipped to the client; in `.razor` it is discarded.
- Is a Razor comment `@* *@` a "comment"? It is the Razor equivalent of `/* */`.
- Does "generated code is excluded" still hold if the C# in `@code` is reported? (It is generated C#, but written by a human.)
- Is a diagnostic without a code fix acceptable for Razor files?
